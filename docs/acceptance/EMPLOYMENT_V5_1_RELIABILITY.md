## 阶段 1 — 评论层级与去重修复

- 日期：2026-11-10
- 审计问题：
  - 知乎 action 把 `.CommentContent` 全部标为一级评论，并按文本全局去重，可能把楼中楼误当一级、把不同楼层的相同文本合并；
  - 小红书 action 只解析一层 `.reply-container`，未递归处理更深回复。
- 真实 DOM 验证（知乎问题页评论区）：
  - 一级评论缩进约 91 px，楼中楼约 125 px；
  - 修复后一次解析得到 7 条一级评论、11 条楼中楼，父子关系正确；
  - 相同文本出现在不同楼层时保持为两个独立节点。
- 修复：
  - 知乎按 `getBoundingClientRect().left` 与首个评论的缩进差判定层级；回复挂到当前一级评论；去重键包含层级与父索引，不再全局按文本合并；
  - 小红书 `parseReplies` 递归处理 `reply-container`，支持二级及更深回复；
  - `extraction.py` 保持嵌套树与任意层级计数。
- 测试：`python -m unittest discover -v` → **89 个测试全部通过**（新增多层回复/同文本跨父节点测试）。
- 边界：知乎问题页正文中可能同时出现多个“N 条评论”，`displayed_total` 的页面计数在问题页可能不唯一；本次层级修复不代表问题页评论总数已精确。专栏页仍按单一计数处理。
- 提交：中文提交并推送 `origin/main`；SHA 记录于阶段 6 交付表。

## 阶段 3 — 搜索发现、URL 队列与文章定位

- 日期：2026-11-10
- 7 个失败候选分析：
  - 批次日志均为 `RuntimeError: 目标卡片未找到`，发生在“分组关键词搜索 + 精确标题兜底”之后；
  - 小红书搜索卡片标题会截断/改写，且结果顺序与卡片集合在发现和采集之间会变化；
  - 用标题片段匹配 `link` 文本不可靠；随后站点返回“安全验证”，未继续重试。
- 修复：
  - 新增 `scripts/employment/browser/discovery.py`：把 `/search_result/<id>?xsec_token=...` 规范化为 `/explore/<id>`，知乎去掉 query/fragment；按 URL 去重、与已知文章过滤、生成队列；
  - `actions.py` 增加 `DISCOVER_XHS_RESULTS` / `DISCOVER_ZHIHU_RESULTS`，只读取搜索结果链接，不进入详情；
  - `runner.py` 新增 `queue` 子命令：支持 `--known-json` 或 `--db` 读取已知 URL，输出 new/duplicate/queue；
  - 后续定位应使用队列中的规范化 URL/笔记 ID，而不是标题片段。
- 记录方式：搜索发现与详情采集分开记录；发现阶段不计入文章数，只有详情页+评论+入库+Markdown 完成才算一篇。
- 测试：`python -m unittest discover -v` → **95 个测试全部通过**（新增发现/队列/CLI 测试）。
- 未访问平台；未修改历史数据。
- 提交：中文提交并推送 `origin/main`；SHA 记录于阶段 6 交付表。

## 阶段 4 — 小红书批次恢复（部分完成，7/8）

- 日期：2026-11-10
- 用户完成小红书 APP 扫码验证后，搜索页恢复。
- 首次重试 0/7：定位到卡片但因点击目标错误未进入详情。
- 根因（真实 DOM）：
  - 每个搜索结果卡片包含一个**隐藏的** `<a href="/explore/<id>">`，排在最前；
  - CSS 选择器 `a[href*="<id>"]` 命中了隐藏链接，点击无效；
  - 真正可进入详情的是带 `xsec_token` 的 `a.title[href*="/search_result/<id>"]`。
- 修正：点击 `a.title[href*="<id>"]`（或 `search_result/<id>`），不再使用通用 href 选择器。
- 恢复结果：`v5-xhs-8` 从 1/8 提升到 **7/8**；新增 6 篇，均完成详情、评论、入库与 Markdown；`v5_06` 仍未找到卡片。
- 数据：Campaign 25 → **31/1000**；评论总数 378；批次 `v5-xhs-8` 状态 `partial`。
- 安全：仅在用户完成扫码后继续；未绕过验证、未提高频率。
- 提交：中文提交并推送 `origin/main`；SHA 记录于阶段 6 交付表。

## 阶段 6 — 调度器决策与最终报告

- 日期：2026-11-10
- 决策：**暂不开发长期运行的 Campaign 调度器**。
  - 目前 runner 是短批执行 + checkpoint，浏览器动作仍由宿主 Agent 触发；
  - 尚未证明无人工停顿的连续吞吐，也没有两个干净批次的失败率/恢复率样本；
  - 先稳定搜索发现、评论层级与批次恢复，再评估调度器。
- 重新评估调度器的前提：
  1. 至少两个连续、无长时间人工停顿的新批次；
  2. 每批 ≥10 篇，文章失败率 <10%；
  3. checkpoint 恢复验证通过，重复导入不产生重复数据；
  4. 端到端有效吞吐（含发现、评论、入库、Markdown）稳定在可接受区间。
- 最终核对：
  - `research_items=33`（Campaign 31 + 历史 2）；`research_comments=378`（一级 224、楼中楼 154）；
  - `research_artifacts=73`，文件 SHA 与数据库一致（0 不一致）；
  - `PRAGMA integrity_check=ok`，外键违规 0；
  - 离线测试 **95 个通过**；`doctor` PASS=9 / WARN=0 / FAIL=0。
- 未完成：两个干净连续批次、剩余 969 篇、XHS `v5_06` 单篇、3 篇知乎评论不可用。
- 提交：中文提交并推送 `origin/main`；SHA 记录于阶段 6 交付表。
