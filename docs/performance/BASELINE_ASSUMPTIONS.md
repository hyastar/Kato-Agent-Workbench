# V5 基线假设与约束

## 1. 待检验假设

1. 宿主 Agent 每次点击/展开/读取前都推理一次，串行工具往返占比可能过高。
2. 页面快照重复返回大块 DOM/可访问性树，带来传输、Token 与上下文开销。
3. 已确定的重复步骤没有沉到一次可复用的浏览器执行单元。
4. 评论与楼中楼的动态展开、等待、滚动是主要耗时。
5. Campaign/Batch 只是数据管理，不等于可长期独立运行的浏览器 Worker。

以上均为假设，未经实测不得声称“已定位瓶颈”或“快 N 倍”。

## 2. 已知事实（V4 基线）

- 真实样本 20 篇（小红书 16、知乎 4）。
- 一级评论 211、楼中楼 154。
- 评论覆盖 complete 9 / partial 8 / not_available 3。
- SQLite V3、Campaign `employment-2026-2027-1000-20261109`，实际 20/1000。
- 离线测试 73 个通过。
- 已发现缺陷：`select_comments()` 在无“最新排序”证据时把采集顺序倒序当作 latest；已改为默认 `high_likes`，只有 `latest_verified=True` 才标 `latest`。

## 3. 测量边界

- 不测 Token（宿主无真实指标时记 `null`）。
- 不把搜索结果数量当文章数。
- 不把打开页面但未处理评论的条目算完成。
- 不把演示 fixture 计入真实数据。
- 不把楼中楼计入 50 条一级评论配额。
- 不因页面缓存、网络波动或评论较少而直接推断架构优势；报告中说明混淆因素。

## 4. 混淆因素

- 网络与站点响应波动；
- 浏览器冷/热缓存；
- 页面评论数量随时间变化；
- 登录状态与风控提示；
- 页面结构随平台更新；
- 同一样本重复访问可能触发不同加载行为。

## 5. 安全与权限

- 仅访问任务白名单内的知乎、小红书页面。
- 登录、验证码、设备确认由用户在可见 Chrome 中完成。
- 不绕过访问控制、不调用隐藏接口、不使用代理池或指纹伪装。
- 不保存作者身份信息与联系方式，不做任何互动。
